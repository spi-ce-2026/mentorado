  - uberhub-api-gateway: application.yml roteia somente /uberhub-<serviço>/**
    para localhost:8081-8085. Não há rota /api/v1. Há um predicado com erro de
    digitação: Path=?uberhub-auth-service/** (deveria ser /). Logo, o gateway
    do repositório NÃO é o que responde em produção: a URL de produção responde
    em /api/v1/... mas o código do repositório não tem essa rota.
  - uberhub-mentorship-service: MentorshipController tem apenas
    @RequestMapping("/api/v1/mentorships") e um comentário TODO para POST /.
    MentorshipService.create também é TODO. Ou seja, POST /mentorships NÃO está
    implementado no código do repositório (último push 2026-11-18).
    VoucherController está em /api/v1/vouchers: /generate, /mentor, /redeem,
    /validate/{code}. O app usa /admin/vouchers/*, que não aparece nos
    controllers do admin-service.
  - uberhub-admin-service: /admin/dashboard, /admin/mentors/pending,
    /admin/mentors/{id}/approve. Não há controller de /tags (existe apenas a
    entidade AdminTags).
  - uberhub-profile-service: apenas /profiles (GET, POST, /health).
  - uberhub-auth-service: /auth/register, /auth/login, /auth/refresh,
    /auth/recover-password. Não há /users/me.
  - Conclusão: o código dos repositórios não implementa POST /mentorships, o
    /tags nem /users/me. O gateway de produção responde em rotas que o código
    dos repositórios não contém. Não é possível dizer, a partir daqui, qual
    código está implantado. Não se considera o backend integrado.

3.4 Contrato do payload (comparação app x docs/openapi-mentorado.yaml)
  Enviado pelo app (src/services/mentorshipService.js, buildPreferences):
    { "preferences": { "expertise": [...], "availableTimes": [],
      "preferredLanguage": "Português", "sessionFormat": "online" } }
  - Estrutura e campos batem com MentorshipRequest do contrato.
  - expertise: o contrato diz que os nomes vêm de GET /tags. O app usa os nomes
    retornados pelo catálogo.
  - Exemplo do pedido ("Java", "Dados"): esses nomes NÃO existem no catálogo
    atual (existem, por exemplo, "Java Spring Boot" e "Data Analytics"). O
    exemplo não é válido como está; não foi usado no app.
  - preferredLanguage ("Português"/"Inglês"), sessionFormat ("online"/
    "presencial") e availableTimes: valores provisórios. O contrato marca
    "a confirmar com o backend" (proposta de redesign, decisão 7.8). O app
    não alterou o formulário: a lista de horários segue vazia.
  - Erro: o contrato define ErrorResponse com o campo "error". O app lê
    error.response.data.error, portanto a correspondência está correta.
